# Модуль Requests

## Зона ответственности

Это центральный модуль. Он создаёт и читает заявки, связывает их с автором, аудиторией, услугой,
статусом, согласующим и исполнителем. Правила перехода статусов должны жить в workflow, а не в REST controller.

## Что уже есть

- `RequestEntity`, `AudienceEntity`, `RequestStatusEntity`;
- JPA-связи с `UserEntity` и `ServiceCatalogEntity`;
- repositories для заявок, аудиторий и статусов;
- интерфейс `RequestService`;
- начальные статусы в Flyway.

## Критичные несоответствия

1. `ServiceRequestRepository` назван по старому имени. Переименовать в `RequestRepository`.
2. `RequestService` возвращает entity, а `listByAuthor` — неограниченный `List`. Нужны DTO и `Page`.
3. `create(Long userId, ...)` позволяет клиенту выдать себя за другого. Автора нужно брать из `CurrentUser`.
4. `changeStatus` принимает любой status ID и обходит workflow. Этот метод нужно удалить из публичного контракта.
5. `created_at` имеет `DEFAULT now()` и `NOT NULL`, но Hibernate может вставить `NULL`. Добавить `@CreationTimestamp` или
   `@Column(insertable = false, updatable = false)` и перечитывать entity. Проще для учебного проекта — `@CreationTimestamp`.
6. Нет `@Version`: два сотрудника могут перезатереть назначение или статус. Добавить `version bigint NOT NULL DEFAULT 0`.
7. Нет истории статусов. Без неё нельзя объяснить, кто и когда изменил заявку.
8. `is_approved` дублирует часть смысла статуса. Нужно точно описать, какое именно согласование оно обозначает.

## Целевая модель статусов

```text
PENDING_HEAD
   ├─→ PENDING_DEPARTMENT
   └─→ REJECTED

PENDING_DEPARTMENT
   ├─→ ASSIGNED
   └─→ REJECTED

ASSIGNED → IN_PROGRESS → DONE
    └───────────────────→ CANCELLED
IN_PROGRESS ──────────────────→ CANCELLED
```

Команда должна решить, может ли автор отменить `PENDING_HEAD`/`PENDING_DEPARTMENT` и можно ли возвращать заявку из
`IN_PROGRESS` в `ASSIGNED`.

## Миграции

Минимально нужны:

```sql
ALTER TABLE request
    ADD COLUMN version bigint NOT NULL DEFAULT 0;

CREATE TABLE request_status_history (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    request_id bigint NOT NULL REFERENCES request(id),
    from_status_id smallint REFERENCES request_status(id),
    to_status_id smallint NOT NULL REFERENCES request_status(id),
    changed_by bigint NOT NULL REFERENCES users(id),
    changed_at timestamptz NOT NULL DEFAULT now(),
    reason text
);

CREATE INDEX idx_request_history_request
    ON request_status_history(request_id, changed_at);
```

## Пример создания

```java
@Transactional
public RequestDto create(CreateRequestRequest command) {
    UserEntity author = userRepository.getReferenceById(currentUser.id());
    AudienceEntity audience = audienceRepository.findById(command.audienceId())
            .orElseThrow(() -> new EntityNotFoundException("Audience not found"));
    ServiceCatalogEntity service = catalogRepository.findByIdAndActiveTrue(command.serviceId())
            .orElseThrow(() -> new EntityNotFoundException("Active service not found"));
    RequestStatusEntity status = statusRepository.findByName("PENDING_HEAD")
            .orElseThrow(() -> new IllegalStateException("Initial status is not configured"));

    RequestEntity request = new RequestEntity();
    request.setAuthor(author);
    request.setAudience(audience);
    request.setService(service);
    request.setStatus(status);
    request.setDescription(command.description());

    RequestEntity saved = requestRepository.save(request);
    eventPublisher.publishEvent(new RequestCreatedEvent(saved.getId(), author.getId()));
    return RequestMapper.toDto(saved);
}
```

`findByIdAndActiveTrue` появится только после добавления `active` в catalog.

## Правила видимости

- `TEACHER` видит свои заявки;
- `DEPARTMENT_HEAD` и `DEPARTMENT_STAFF` видят заявки авторов своего отдела;
- `DUTY_OFFICER` видит назначенные ему заявки;
- `ADMIN` видит все заявки.

Проверять эти правила нужно в сервисе и в repository query/specification, а не фильтровать уже загруженный список в Java.

## Тесты

- автор берётся из security context;
- неизвестные audience/service дают `404`;
- неактивная услуга не принимается;
- созданная заявка имеет `PENDING_HEAD` и непустой `createdAt`;
- чужая заявка не раскрывается через `GET /requests/{id}`;
- пагинация и фильтры совместимы;
- конкурентное изменение даёт `409 Conflict`, а не тихо затирает данные.

## Детальная декомпозиция задач

### REQ-01. Реализовать справочник аудиторий

Почему отдельно: без audience нельзя создать request, но это простой CRUD-справочник.

Шаги:

1. Добавить `existsByNumberIgnoreCase`, paged search.
2. Создать `AudienceRequest`, `AudienceDto`, mapper, service, controller.
3. Договориться о нормализации номера: uppercase, пробелы, дефисы.
4. Добавить soft-active, если аудитории могут выводиться из эксплуатации; иначе не реализовывать DELETE.
5. Доступ: read authenticated, write admin.

Приёмка: duplicate отклоняется; request не теряет audience после изменения справочника.

### REQ-02. Подготовить migration Request V2+

Зависит от решения CAT-06.

Добавить:

- `version bigint NOT NULL DEFAULT 0`;
- `deadline_hours_snapshot integer NOT NULL`;
- `due_at timestamptz NOT NULL`;
- history table и indexes;
- при наличии старых rows — backfill до NOT NULL.

Порядок для непустой БД:

1. Добавить nullable columns.
2. Заполнить snapshot и due_at join-запросом к catalog.
3. Проверить, что null нет.
4. Добавить constraints.

Тест: migration на clean DB и DB с одной старой request.

### REQ-03. Привести RequestEntity в соответствие с БД

Шаги:

1. Добавить `@Version long version`.
2. Добавить snapshot/due fields.
3. Исправить `createdAt`: `@CreationTimestamp` + `updatable = false` или DB-generated strategy. Выбрать один подход.
4. Добавить `nullable = false` к scalar и join columns согласно схеме.
5. Не добавлять cascade remove к author/audience/service/status.
6. Создать history entity. Её relation к request может быть one-to-many, но не включать history в default RequestDto.

Приёмка: Hibernate validate проходит на PostgreSQL, insert request не падает из-за `created_at`.

### REQ-04. Переименовать repository и описать fetch strategy

1. `ServiceRequestRepository` → `RequestRepository`.
2. Добавить `JpaSpecificationExecutor` или явные query methods.
3. Для details использовать `@EntityGraph`; для page не fetch-join нескольких collections.
4. Реализовать queries сразу с visibility scope, а не после `findAll()`.
5. Разрешить sort только по whitelist: createdAt, status, dueAt, id.

Измерить SQL count в integration-тесте и не допустить N+1.

### REQ-05. DTO и mapper

Создать:

- `CreateRequestRequest`;
- `RequestDto` для details;
- `RequestSummaryDto` для page;
- `RequestFilter`;
- `RequestStatusHistoryDto`;
- nested summary DTO из users/catalog/audience;
- `RequestMapper`.

В summary не класть description/history/checklist. В details не класть JPA collections. `approved`/`rejectReason` временно оставить до решения workflow,
затем убрать или точно описать semantics.

### REQ-06. Реализовать create request

Зависит от: SEC-03, CAT-04, REQ-01–REQ-05.

Точная последовательность:

1. Получить author ID из `CurrentUser`.
2. Загрузить author reference/entity; не принимать authorId.
3. Найти active audience/service; вернуть `404`/domain error.
4. Найти `PENDING_HEAD`; если seed сломан, это server configuration error, не client `404`.
5. Рассчитать deadline snapshot/dueAt один раз.
6. Сохранить request, создать initial history `null → PENDING_HEAD`.
7. Создать checklist snapshot, когда CHK будет готов.
8. Опубликовать event.
9. Вернуть DTO после установки generated ID/time.

Всё в одной transaction. Не отправлять email внутри transaction.

### REQ-07. Реализовать get/list/search

Видимость:

1. ADMIN — predicate true.
2. TEACHER — `author.id = currentUser.id`.
3. HEAD/STAFF — `author.department.id = currentUser.departmentId`.
4. DUTY_OFFICER — `executor.id = currentUser.id`; если нужна очередь неназначенных, явно добавить бизнес-правило.

Для GET by ID применять scope в query или сразу после load; чужой object лучше отдавать `404`, чтобы не раскрывать его существование.

Фильтр клиента не может расширить scope, только сузить.

### REQ-08. REST controller

1. GET collection принимает filter и pageable; size cap 100.
2. POST принимает только audience/service/description; `201` + Location.
3. GET details/history/checklist — separate endpoints.
4. Не создавать generic `PATCH /requests/{id}` для status/assignee; все changes через workflow actions.
5. Над каждым endpoint написать role/scope test.

### REQ-09. Набор тестов

- entity mapping + Flyway на real PostgreSQL/Testcontainers;
- create success и каждая missing dependency;
- createdAt/dueAt/version/history initial values;
- visibility matrix 5 roles × own/department/assigned/foreign;
- filters не расширяют scope;
- details entity graph не даёт lazy exception;
- page query не даёт duplicate rows/N+1;
- invalid size/sort/filter дают `400`.
